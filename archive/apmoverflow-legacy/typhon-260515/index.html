  • Notably, there's a differential between runtime-error repair and general unit-test repair
  • The good thing: at least GPT-4 is struggling a lot with passing unit-tests in 1 shot.
  • Last meeting, we were talking about assertion-statements as "WIP" while we plow through the tests
  • There's basically 2 problems:
    • Dynamic runtime-error repair
      • making it never have runtime-errors by-construction
      • fwiw, we might not necessarily need precise tests for this.
      • runtime errors are a clean signal: crash/no crash, traceback, line number
    • Semantic repair
      • making it pass unit-tests by-construction
      • will need unit-tests given for sure.
        • There's a problem of: test-driven dev (TDD) is incomplete by nature, what's the input of what we're trying to test, really?
        • if we give it the entirity of the unit-tests we'll use to evaluate it against, it'll likely overfit and always pass (no benchmarks have this property)
        • if you give only tests, the task becomes test-fitting. If you give all tests, the benchmark collapses. If you give no tests/assertions, there may be too little feedback for a rollout method to use.
      • Unit tests are delayed, partial, and may not localize the cause
      • Assertions could be a way to create intermediate semantic signals, but they are noisy because the assertion itself might be wrong, incomplete, or over-specific
      • also, how will you search through the space of possible "hypotheses" that could pass
  • There's an argument that you need runtime-error repair before semantic repair, but I think the cleaner framing is:
    • Focus on semantic repair first.
    • Within semantic repair, there will probably be points where we asynchronously run unit tests / behavioral tests / assertions.
    • During those runs, we may encounter runtime errors.
    • Those runtime errors can be treated as one class of semantic-repair feedback that we later fix, rather than the whole research target.
    • So runtime-error repair is a subcase / guardrail inside the semantic-repair loop, not necessarily a prerequisite that must be solved first.
  • I do worry, though, that all of this unit-test passing w/ intermediate assertions might cause issues with overall response quality due to overfitting (proxy objective over-fitting)
    • Could work w/ hard constraints vs soft warnings?

Papers worth talking about

  • Towards Agentic Runtime Healing / Healer (Sun et al., arXiv 2024/2026)
    • This is probably the cleanest "LLM as runtime-error handler" paper.
    • The setup: program hits an unhandled runtime error, Healer grabs the error message/location/source context/runtime state, asks an LLM for a small healing snippet, executes that snippet against the current state, then resumes after the failing line.
    • Important: it does not permanently patch the source code. It's runtime state repair / dynamic exception handling, not normal program repair.
      • More concretely, their Python prototype AST-wraps candidate statements in try/except; on failure it prompts the LLM for replacement lines, runs the snippet via exec() in a copied runtime state, diffs the changed variables, merges that delta back, and continues after the failed statement.
    • Their labels are useful: FAIL = still crashes, PROCEED = gets past the failing line, CORRECT = gets past the failing line and matches expected output. So CORRECT is a subset of PROCEED.
    • Main numbers: GPT-4 gets about 73% PROCEED but only about 39% CORRECT; GPT-3.5 is about 48% / 24%; CodeQwen is about 35% / 13%.
    • It seems best at local, state-recoverable errors: missing imports, undefined-but-inferable variables, type fixes, index guards, obvious attribute/name mistakes, or replacing one failing statement.
    • It fails or becomes risky when the snippet itself errors, the needed context is missing, the bug requires broader code changes, or the execution depends on side effects / external resources / control-flow that cannot be locally reconstructed.
    • Caveat: this is Python runtime healing, which is much friendlier than C/C++ land; segfaults, memory corruption, leaks, UB, and harder state introspection/dynamic patching are not really the same problem.
    • The important middle category is PROCEED but wrong: it may skip logic, assign plausible-but-wrong defaults, mask the symptom, corrupt later state, omit returns, or replace APIs in behavior-changing ways.
    • This supports treating runtime-error repair as a guardrail/subcase inside semantic repair, not as the whole target.
